# Amazon Scout — agent's guide to working on, building and releasing this app

This is the root guide for anyone (human or AI) picking up this repository. It is written to be
self-contained: read it before making changes, and keep it accurate when you learn something new.

`client/AGENTS.md` holds client-specific conventions and takes precedence inside `client/`.

---

## 1. What this app is

A serverless Android app for resellers. Point it at a barcode and it tells you what the item is,
what it sells for, and whether it is restricted for Amazon. There is **no backend and no API key
anywhere** — it scrapes public HTML and talks to keyless endpoints directly from the phone.

| | |
|---|---|
| Framework | Expo SDK **57** (`expo` ~57.0.24), React Native 0.86.3, React 19.2.3 |
| Language | **Plain JavaScript.** No TypeScript anywhere |
| Navigation | **None.** One screen plus `useState` booleans toggling `<Modal visible>` |
| Distribution | Signed APK on GitHub Releases, with an in-app updater |
| Package name | `com.amazonscout.app` |
| Repo | `ByzantineEmpress/amazon-scout-app` |

Current version lives in **`client/app.json` → `expo.version`**. Read it rather than trusting any
number written in this document.

### The three ways in

1. **Barcode scan** (the main screen) — the original feature, for books/DVDs/games.
2. **📖 Printed ISBN** — OCR for books too old to have a barcode, plus title search for
   pre-1970 books.
3. **📷 Photo Comps** — photograph any non-book item and search its eBay sold listings.

## 3. Data flow

```
App.js
 └─ scanBarcode(code, marketplace)          services/api.js
      └─ processBarcodeScanOnDevice()       services/barcodeService.js
           ├─ scrapeAmazonSearch()          amazon.ca / amazon.com search HTML, regex-parsed
           ├─ fetchOpenLibrary()            openlibrary.org
           ├─ fetchAppleBooks()             itunes.apple.com
           ├─ fetchUPCItemDb()              api.upcitemdb.com   (non-book media)
           ├─ fetchAbeBooksPrice()          abebooks.com        (used-book pricing)
           └─ evaluateRestrictions()        services/gatingRules.js  (pure, local, offline)
      └─ storage.js                         AsyncStorage: settings, history (100 max), offline queue
```

Two more paths run alongside it:

- **Photo comps**: `ItemCompsModal` → still-photo barcode decode + ML Kit OCR →
  `guessItemName` / `findModelNumber` → `ebayService` → eBay sold search rendered in
  `EbayCompsModal` (an in-app WebView).
- **Printed ISBN**: `IsbnScanModal` → OCR → `extractIsbnCandidates` → two-frame confirmation →
  the normal `scanBarcode` pipeline.

### The pure modules (and why that matters)

`gatingRules.js`, `barcodeValidation.js`, `isbn.js`, `titleScan.js`, `ebayQuery.js` and
`ebayHtml.js` are **dependency-free** — no `import` statements. The test files load them by
reading the source and stripping the `export` keywords, which only works while they stay
self-contained. Keep them that way, and put any new pure logic in a module like them rather than
in a component. See §6.

## 4. Invariants

These are not style preferences. Each one is here because breaking it caused a shipped bug.

### 4.1 Plain JS, one screen, no router

`index.js` calls `registerRootComponent(App)` and `App.js` renders everything. Do not introduce
`expo-router`, `react-navigation`, a `src/app/` tree or `_layout.tsx` files — that would be a
rewrite of working, released code.

### 4.2 Native modules must be required lazily

The ML Kit OCR package calls `requireNativeModule` **at module load**, which throws wherever the
native code is absent — Expo Go above all. A top-level import in a file that `App.js` imports
statically therefore takes down the *whole app at startup*, for users who never open that screen.

```js
let recognizeTextModule = null;

function getRecognizeText() {
  if (!recognizeTextModule) {
    recognizeTextModule = require('@infinitered/react-native-mlkit-text-recognition');
  }
  return recognizeTextModule.recognizeText;
}
```

Do this for every native module that is not bundled in Expo Go. `expo-file-system`,
`expo-camera`, `expo-clipboard`, `expo-intent-launcher` and `expo-web-browser` are in Expo Go and
are safe to import normally.

### 4.3 Only one `CameraView` may be alive at a time

Android does not error on a second camera — it renders **black**. Both camera screens therefore
unmount the main viewfinder while they are open:

```jsx
{isbnScanVisible || itemCompsVisible ? (
  <View style={styles.camera} />
) : (
  <CameraView ... />
)}
```

expo-camera's `active` prop looks purpose-built for this but is **iOS-only**, so it does not help
on Android. Also mount the new screen's camera ~350 ms late, so the previous one has released the
device.

### 4.4 The camera preview is full-bleed

A camera in a fixed-height box does not fill it: the video occupies the top of the box and the
rest stays black. This was shipped twice before the cause was found. Float the controls over a
full-screen preview instead — that arrangement also gives ML Kit a larger image.

### 4.5 Every hook goes above every early return

`ScanResultModal` has an early `return null` when there is no item. An effect added *below* it
meant the component ran a different number of hooks between renders, and the app **crashed the
moment a scan set the item** (v1.0.9). ESLint's `react-hooks/rules-of-hooks` catches this — it is
the single most valuable check in `npx expo lint`. Keep the guard below all hooks and keep the
comment that says so.

### 4.6 Scrapes must degrade, never throw

`scrapeAmazonSearch` parses raw HTML and is inherently brittle: a markup change, a CAPTCHA or a
429 makes it return `null`. Callers treat `null` as "no data" and fall back to the other sources.
Preserve that: **never let a scrape failure crash a scan**, and never let one source's failure
hide the others' results.

### 4.7 Gating verdicts are advisory

`evaluateRestrictions` is a local heuristic — publisher/studio keywords, an ISBN-prefix table, and
a "DVD MSRP ≥ $25" rule. Real gating is account-, category- and condition-specific. A
`HARD_GATED` verdict is a prompt to verify in Seller Central, not an answer. Word it that way.

### 4.8 `marketplace` is always a parameter, default `'CA'`

Amazon.ca/CAD is the default. Any new pricing or URL logic must handle `'CA'` and `'US'`.

### 4.9 expo-file-system: use the class API

In SDK 57 the legacy namespace throws at runtime — `FileSystem.deleteAsync` and
`FileSystem.downloadAsync` are traps that look correct and fail on device.

```js
import { File, Directory, Paths } from 'expo-file-system';

new File(uri).delete();                                  // not deleteAsync
await File.downloadFileAsync(url, directory, { idempotent: true, onProgress });
```

### 4.10 Verify API shapes against the installed package, not memory

Expo ships breaking changes every release. For anything touching an Expo, EAS or React Native API:

1. Read the `expo` major version in `client/package.json` (currently **57**).
2. Fetch the versioned docs: `https://docs.expo.dev/versions/v57.0.0/` (append `.md` for a clean
   Markdown source).
3. **And** check the installed package in `client/node_modules`, because the docs are not always
   the whole truth. The docs list `scanFromURLAsync` as a method on the camera view; in the
   installed build it exists **only as a module-level export**, and the ref form is `undefined` —
   which fails silently inside a `try`/`catch` and looks like "no barcode found".

## 5. The development loop

Run all three of these before saying anything is done. Each proves something the others cannot.

```bash
# from the REPO ROOT
npm test                      # 135 tests across 7 suites, no network needed

cd client
npx expo lint                 # 8 errors / 18 warnings at the time of writing, all pre-existing
npx expo export --platform android --no-bytecode --output-dir dist
rm -rf dist                   # proves Metro can bundle: imports resolve, no syntax errors
```

Per-suite counts at the time of writing, so drift is visible: gatingRules 15, releaseSigning 9,
barcodeValidation 28, isbn 27, titleScan 24, ebayQuery 17, ebayHtml 15.

- **`npm test`** covers the pure logic — validation, extraction, query building, HTML parsing and
  the gating rules.
- **`npx expo lint`** catches hook violations and undefined variables. It earned its place by
  catching a leftover `barcode` reference after a prop rename, and by reproducing the v1.0.9
  crash. Treat the numbers above as a reference point rather than a contract: **run lint before
  and after your change and make sure you added nothing**, and leave the pre-existing findings
  alone unless asked to clean them up.
- **`npx expo export`** is the only local check that the app actually builds as a bundle.

Stack traces are useless without source maps in a release build, so prefer adding a test over
adding a `console.log`.

### What these cannot tell you

There is **no JDK and no Android SDK on this machine**, so the Android build can only be validated
in CI. And nothing local can tell you how the camera behaves — that needs a device.

### Expo Go

Works for the barcode flow. **Cannot run the OCR screens** (ML Kit text recognition is not in Expo
Go). Because of §4.2 those screens degrade with a message instead of crashing the app, but they
still cannot work there. Use a build.

### Validating a native change without releasing

```bash
gh workflow run release-apk.yml --repo ByzantineEmpress/amazon-scout-app \
  -f tag=v1.0.21-native-test -f dry_run=true
gh run watch <run-id> --repo ByzantineEmpress/amazon-scout-app --exit-status --interval 30
```

~9–11 minutes. It prebuilds, restores the keystore, builds, signs, verifies and uploads the APK as
an artifact — and **publishes nothing**. On a dry run the tag/version and release-notes checks are
skipped, so any tag works. Download the artifact from the run page to test on a device.

This is also how to confirm a new native module was actually linked: grep the build log for
`:infinitered-react-native-mlkit-text-recognition:preReleaseBuild`. A build can succeed while a
native module is silently absent from the APK — the JS would only fail at runtime.

## 6. Adding a test

The pure modules have no imports, so a test evaluates their source directly. Copy this shape:

```js
import { createRequire } from 'node:module';
import { fileURLToPath } from 'node:url';
import fs from 'node:fs';
import path from 'node:path';

const require = createRequire(import.meta.url);
const here = path.dirname(fileURLToPath(import.meta.url));

const source = fs.readFileSync(path.join(here, '..', 'src', 'services', 'myModule.js'), 'utf8');
const { myFunction } = new Function(
  `${source.replace(/^export /gm, '')}\nreturn { myFunction };`
)();
```

Then add the file to the `test` script in the **root** `package.json` — it is a chain of
`node …test.mjs && …` commands, so a new file that is not listed never runs.

`scripts/release.mjs` is tested the same way (`client/test/releaseSigning.test.mjs` reads the
plugin source and asserts it repoints the release build type).

**Write the test for the bug you just fixed, and hand-verify the expected values** rather than
deriving them from the code under test. Two examples where tests caught real defects before they
shipped: a compliance-marks photo producing the query `EN71 ASTM F963 RoHS`, and a sticker-only
photo producing the doubled query `CUH-ZCT2U CUH-ZCT2U` (eBay ANDs its terms, so both would have
returned nothing).

## 7. Releasing

### The command

```bash
# from the REPO ROOT — it bumps both version files, scaffolds the notes, tests, then commits,
# tags and pushes, which is what triggers the APK build
npm run release -- 1.0.21

npm run release -- 1.0.21 --dry-run    # every local step, touches no git history
npm run release -- 1.0.21 --no-edit    # never open an editor; fail if the notes are a stub
```

Write `release-notes/v1.0.21.md` first if you want the notes to be yours; otherwise the script
scaffolds it from `_template.md` and opens `$EDITOR` (Notepad on Windows).

### What preflight enforces

- You are on `main`.
- The tree is clean **except** for the three files a release owns (`client/app.json`,
  `client/package.json`, `release-notes/v<version>.md`) — other dirty files mean a release tag
  would sweep up unrelated work.
- The tag `v<version>` does not already exist.
- The version is strictly higher than the current one. The in-app updater only offers an update
  when the release tag is *higher* than the installed version, so reusing or lowering a number
  means users are never told about the release.
- The notes file no longer contains the template marker `<!-- TODO:`.
- `npm test` passes.

### The contract between the repo and the updater

Three things must agree or users are either never offered an update, or are offered one that never
clears after installing:

1. `release-notes/v<version>.md` **must exist** — CI fails before building without it.
2. `client/app.json` → `expo.version` must equal the tag minus the `v`. CI re-checks this.
3. The tag must be higher than the version the user has installed.

### Writing the notes

The app shows the **first three lines** in its "update available" card, so lead with the one thing
a user needs to know, in their language, not a changelog. Then `### ✨ New` / `### 🐛 Fixed` /
`### ✅ Unchanged`. CI appends `_install-instructions.md` automatically — do not repeat it.

### What CI does

`.github/workflows/release-apk.yml`, triggered by a `v*` tag push:

1. Verifies the tag matches `expo.version`; resolves and appends the notes.
2. Verifies all four signing secrets exist (see §8).
3. `npm install` in `client/`, then `npx expo prebuild --platform android --clean`.
4. Restores the keystore to `client/android/app/release.p12` — **after** prebuild, which recreates
   `android/` from scratch — and opens it with `keytool` to prove the password matches.
5. `./gradlew assembleRelease`.
6. Runs `apksigner verify --print-certs` and **fails if the APK is debug-signed**.
7. Uploads the artifact, then publishes the release.

Java 17, Node 22. `npm install` (not `npm ci`), so `client/package-lock.json` is committed but not
treated as authoritative.

### Verifying a release

```bash
gh release view v1.0.21 --repo ByzantineEmpress/amazon-scout-app
gh release view v1.0.21 --repo ByzantineEmpress/amazon-scout-app --json assets --jq '.assets[].name'
gh api repos/ByzantineEmpress/amazon-scout-app/releases/latest --jq '.tag_name'
```

Confirm: not a draft, the `AmazonScout-v1.0.21.apk` asset is attached, and `latest` equals
`client/app.json`'s version.

## 8. Signing and secrets

**Every APK must be signed with the same private key**, or Android refuses to install it over an
existing copy. The release build deliberately fails rather than falling back to a throwaway or the
public **Android debug keystore** — either would let a stranger publish an APK that a phone accepts
as a genuine Amazon Scout update. `client/plugins/withReleaseSigning.js` repoints the release build
type, and `client/test/releaseSigning.test.mjs` plus a CI step both fail loudly if that regresses.

Four repository secrets: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.

The keystore is PKCS#12, alias `amazonscout`, certificate SHA-256
`4F:F8:44:AB:8A:E3:2E:13:E0:D1:68:38:FD:73:41:C9:32:49:74:4E:03:80:3A:37:61:1E:4A:91:11:B1:2A:99`.
It is never committed (`.gitignore` covers `*.keystore`, `*.jks`, `*.p12`, `*.key`, `*.b64`) and it
is not recoverable from this repository.

> **If the keystore is lost, this app can never be updated again** — it would have to be published
> under a new package name. It exists in GitHub secrets (write-only: you cannot read it back) and
> in the owner's offline backup. Treat that backup as the only copy.

`README.md` §"Release signing" documents the one-time setup and how to recreate a keystore.
APKs published before v1.0.8 were debug-signed, so those installs need **one uninstall** before
in-app updates work.

**Never paste a token into a chat, a source file, or a repository URL.** A token in a remote URL is
written to `.git/config` in plaintext and leaks the moment the folder is copied or shared. Credential
scanning runs in CI (`.github/workflows/secret-scan.yml` → `scripts/secret-scan.sh`, which checks the
worktree and the full history and reports locations only).

## 9. Working in this environment (Windows)

- The agent terminal on this machine is **git-bash / MSYS `bash`**, not PowerShell: use POSIX syntax (`ls`, `grep`, `&&`, single-quoted strings). Paths passed to *native* tools (git, node, gh, curl) are not translated, so give them forward-slash `C:/Users/...` paths (or `$LOCALAPPDATA/Temp` for scratch); MSYS-style `/c/Users/...` and `/tmp`/`/dev/null` break native binaries (curl exit 23, git "cannot change to"). Human operators using PowerShell directly should still note: `>` redirection in PowerShell 5.1 writes UTF-16, which silently corrupts UTF-8 files (emoji, accents) — use the editor tool for file contents, or `cmd /c "… > file"` if you must redirect.
- **`>` redirection in PowerShell 5.1 writes UTF-16**, which silently corrupts UTF-8 files
  (emoji, accents). Use the editor tool for file contents, or `cmd /c "… > file"` if you must
  redirect.
- **Keep CLI output ASCII.** Emoji and box-drawing characters get mangled in captured output. The
  repo's own scripts are written to print ASCII for this reason.
- `warning: in the working copy of '…', LF will be replaced by CRLF` is benign — ignore it.
- Long commands: run them in the background and collect the result, rather than blocking. A CI
  build is 9–11 minutes.
- `gh` is installed and authenticated. MSYS `bash` and `openssl` are available when needed for
  base64 work.
- Approvals for sandbox escalation are disabled, so never request them — they are rejected.

## 10. Domain knowledge the code depends on

**Books and barcodes.** Book barcodes are always numeric EAN-13 beginning `978` or `979`. The
letter `X` appears in *printed* ISBN-10s (and in ASINs derived from them) but **never inside a
barcode**, because a barcode cannot encode it. The ISBN system began in 1970, so older books have
no number at all — that is what the title-search path is for.

**Validation is the safety net.** Every scanned code is checked against its GS1 check digit, and a
number is only accepted after **two agreeing frames**. A misread digit breaks the checksum, so a
wrong number is dropped rather than looked up. Do not weaken this to make scanning feel faster.

**eBay searches AND their terms.** `_nkw` requires every word to appear in a listing, so one wrong
or over-specific term returns *nothing* rather than slightly worse results. This shapes everything:
subtitles and series asides are stripped from queries, a model number is only folded into a
descriptive name when that name is a single word, and sellers list books by title and gear by model
number — never by ISBN or UPC.

**Amazon prices come from scraped search HTML** and are therefore best-effort. Show them as such.

## 11. Bug history — read this before touching these areas

| Symptom | Root cause | Where |
|---|---|---|
| App crashed the moment a scan set an item | A hook was added below the early-return guard | `ScanResultModal.js` §4.5 |
| Releases were signed with the public debug key | The workflow's regex for `buildTypes { release {` never matched, so the patch silently did nothing | `plugins/withReleaseSigning.js` |
| Scanned "barcodes" that were not barcodes | `qr` was enabled and `normalizeBarcode` strips non-digits, so a URL became a plausible number | `barcodeValidation.js` |
| A valid UPC-A was read out of a 13-digit ISBN | The add-on rule stripped *any* trailing digits instead of only 2 or 5 | `isbn.js` |
| Book eBay comps found nothing | The code searched by ISBN whenever one existed, and sellers do not type ISBNs | `ebayQuery.js` |
| Photo Comps camera showed black | Two `CameraView`s were mounted at once; Android gives the second one black | `App.js` §4.3 |
| ISBN screen camera showed black below the image | The preview was in a fixed-height box it would not fill | §4.4 |
| A shutter clicked repeatedly while reading a number | `takePictureAsync` defaults to `shutterSound: true` and it ran every 0.7 s | `IsbnScanModal.js` |
| "No barcode found" forever on still photos | `scanFromURLAsync` was called on the view ref; it is a module-level export only | `ItemCompsModal.js` §4.10 |
| Photo Comps searched for `EN71 ASTM F963 RoHS` | Compliance marks look exactly like product text | `titleScan.js` |
| A sticker photo searched for `CUH-ZCT2U CUH-ZCT2U` | The model was both the guessed name and the appended model | `titleScan.js` |
| Sell-through read **0%** when the count was merely unreadable | `Number(null)` is `0`, so a missing count was coerced into "nothing sold" | `ebayHtml.js` |
| The release script mis-parsed the first dirty file | `git status --porcelain` output was `.trim()`ed, eating the leading column | `scripts/release.mjs` |

## 12. Definition of done

Before you say a change is finished:

- [ ] `npm test` passes from the repo root (and you added a test for the bug you fixed).
- [ ] `npx expo lint` from `client/` shows **no new** errors or warnings.
- [ ] `npx expo export --platform android --no-bytecode` succeeds.
- [ ] Any new native module or `app.json` change was validated with a **dry run** (§5), not just
      assumed to build.
- [ ] Camera behaviour was confirmed on a device, or you have said clearly that it was not.
- [ ] No secret, token, keystore or password is in the diff.
- [ ] If you changed what the app does, the release notes say it in the user's language.
- [ ] Anything you learned that contradicts this document has been written back into it.
